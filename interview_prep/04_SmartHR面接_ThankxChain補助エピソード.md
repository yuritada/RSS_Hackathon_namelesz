## 1. プロダクト概要

### 何を解決するプロダクトか

現代のSNSに蔓延するネガティブな投稿（誹謗中傷・炎上）に対して、
**「日常の小さな感謝や行動が誰かの善意に連鎖する世界」** を作るSNS。

ブロックチェーンの「連鎖・不変性・透明性」というコンセプトをSNSに応用し、
感謝投稿（Thanks）が次の行動投稿（Action）を生み出す連鎖をツリー構造で可視化する。

### 誰のどんな課題を解決するのか

- **SNS疲れを感じているユーザー**：感謝だけを扱う空間を提供
- **「誰かの役に立ちたい」が踏み出せないユーザー**：他者の感謝を見ることで行動の動機づけ
- **善意が広がる様子を見たいユーザー**：連鎖の可視化によって達成感を提供

### 初期案（SNS型）からどう変わったか

**初期案：** タイムラインに感謝投稿が流れる一般的なSNS形式  
**最終形：** 感謝投稿がランダムに海を漂い、誰かが拾って次の行動につなげるボトルメール型

### SNS型からボトルメール型に変えた理由

タイムライン型だと「フォロワー数・いいね数が多い人の投稿が目立つ」構造になり、
既存SNSと同じ承認欲求ゲームを再現するだけになってしまう懸念があった。

ボトルメール型にすることで：
- 誰の感謝も等しく届く可能性がある（フォロワー数不問）
- 「偶然出会った感謝」という世界観とコンセプトが一致する
- ユーザーが「受け取る側」としてポジティブな感情を得やすい

### 善意の連鎖をどう表現しているか

Thanks投稿 → Action投稿（返信） → さらなるAction（連鎖）をツリー構造で可視化（ChainView）。
各ノードを `depth`（階層）でY方向に配置し、感謝がどう広がったか一目でわかる。
ノードをクリックすると詳細が開き、Panzoomライブラリでズーム・パン操作が可能。

## 3. Firestore 設計

### posts コレクションのドキュメント構造

`posts/core.js` の `addThanksPost` / `addNextAction` から確認した実際の構造：

```javascript
{
  // 基本情報
  type: "thanks" | "action",
  text: string,
  feeling: string | null,
  tags: string[],

  // 投稿者
  authorId: string,          // Firebase Auth UID
  isAnonymous: boolean,

  // メタデータ
  timestamp: Timestamp,      // serverTimestamp()
  likeCount: number,
  actionCount: number,       // この投稿への返信（Action）数

  // チェーン構造（Actionのみ持つフィールド）
  depth: number,             // 0 = Thanks（ルート）、1以上 = Action
  parentPostId: string,      // 直接の親投稿のID
  rootPostId: string,        // チェーン全体の根（Thanks）のID
  parentAuthorId: string,    // 親投稿の著者UID（非正規化）

  // いいね管理
  likedBy: string[],                      // いいねした全ユーザーのUID配列
  likesMap: { [uid: string]: number },    // ユーザーごとのいいね回数（最大10）

  // タスク管理
  savedAsTasks: string[]     // タスク保存したユーザーのUID配列
}
```

### depth / parentPostId / rootPostId の3つが必要な理由

```
Thanks投稿 [depth:0, ID: root_001]
    │
    ├── Action [depth:1, ID: act_001]
    │   parentPostId: "root_001"
    │   rootPostId:   "root_001"  ← 根は常に同じ
    │       │
    │       └── Action [depth:2, ID: act_002]
    │           parentPostId: "act_001"
    │           rootPostId:   "root_001"  ← 根は常に同じ
    │
    └── Action [depth:1, ID: act_003]
        parentPostId: "root_001"
        rootPostId:   "root_001"
```

| フィールド | 役割 |
|---|---|
| `depth` | ChainViewのY座標計算（`top = 100 + depth × 800px`） |
| `parentPostId` | SVGコネクタの描画（どのノードとどのノードを線で結ぶか） |
| `rootPostId` | **チェーン全体を1クエリで取得するためのキー（設計の核心）** |

### ツリー全体の取得方法（`getPostChain` — `posts/read.js` 実コード）

```javascript
export const getPostChain = async (postId) => {
  // 1. 起点の投稿を取得
  const startPostSnap = await getDoc(doc(db, "posts", postId));
  const startPost = startPostSnap.data();

  // 2. rootIdを決定：Thanks自身のIDか、ActionならrootPostIdフィールド
  const rootId = startPost.type === 'thanks'
    ? startPostSnap.id
    : startPost.rootPostId;

  // 3. Thanksルート投稿を取得
  const rootPostSnap = await getDoc(doc(db, "posts", rootId));

  // 4. rootPostId == rootId のAction投稿を1クエリで全取得
  const q = query(postsCollection, where("rootPostId", "==", rootId));
  const querySnapshot = await getDocs(q);

  // 5. フロント用にreplyToフィールドにマッピング（parentPostIdから）
  const posts = [{ id: rootPostSnap.id, ...rootPostSnap.data(), replyTo: null }];
  querySnapshot.forEach((doc) => {
    const data = doc.data();
    posts.push({ id: doc.id, ...data, replyTo: data.parentPostId || null });
  });

  // 6. depthでソートして返す
  return posts.sort((a, b) => (a.depth || 0) - (b.depth || 0));
};
```

### フロント側でのツリー再構築（ChainView.vue の `treeLayout` computed から）

取得したフラットな配列を以下のルールでレイアウト計算：

- **Y座標**：`top = 100 + depth × 800`（depthごとに800pxの縦間隔）
- **X座標**：同一depth内で均等割り `left = (100 / (同深さのノード数 + 1)) × (インデックス + 1)`
- **コネクタ**：SVGの `<line>` 要素で描画、`replyTo` フィールドで親子を判定

`replyTo` はFirestoreには存在せず、`getPostChain` がフロントで `parentPostId` をマッピングして付与している点に注意。

### Firestoreの制約と対応策

| 制約 | 対応策 |
|---|---|
| 再帰クエリ不可 | `rootPostId` を全Actionに持たせ、1クエリでツリー全体を取得 |
| JOINできない | `parentAuthorId` を非正規化して子が親の情報を保持 |
| 参照整合性なし | `tasks` ドキュメントに投稿内容のスナップショットを保持 |
| 1ドキュメント1MB上限 | `likesMap` / `savedAsTasks` がスケール時の課題 |

### なぜRDBやGraphDBではなくFirestoreにしたのか

- バックエンドサーバー不要でフロントから直接接続できる（ハッカソンの時間制約に適合）
- `onSnapshot` によるリアルタイム購読がネイティブサポート
- スキーマ不要でフィールド追加・変更が柔軟
- チーム全員がFirebaseに習熟していた

### スケールした時の課題

1. `likesMap` / `savedAsTasks` 配列：ユーザー数増加でドキュメントサイズが1MB上限に近づく
2. 1チェーンのAction件数増加：全件取得ではフロントのメモリを圧迫する → paginationや遅延ロードが必要
3. Firestoreセキュリティルール：ハッカソン中は緩い設定のままで、本番運用には整備が必須

## 4. UI/UX の工夫

### タイムライン型からランダム表示にした理由

タイムライン型はフォロワー数の多いユーザーが上位を独占し、
既存SNSと同じ承認欲求ゲームを再現するだけになってしまう。

ランダム表示（Firestoreから全件取得後、`selectRandomBottles()` で4件をランダム選択）にすることで：
- 誰の感謝も等しく届く可能性がある
- 「偶然の出会い」というボトルメールの世界観と一致する

「別のボトルを探す」ボタンでは **Firestoreに再アクセスしない**。
取得済みデータからランダム選択することでパフォーマンスも確保している。

### ボトルメールの世界観とアニメーション実装

4種のCSSアニメーションを同時実行して「海を漂うボトル」を表現：

```
bottleJourney  → A地点からB地点へゆっくり移動（35〜55秒）
floatBob       → 上下揺れ（海面の波、6〜11秒）
floatWiggle    → 左右揺れ（3〜6秒）
floatRotate    → 傾き・回転（5〜9秒）
```

各パラメータを `Math.random()` でランダム化しているため、
4つのボトルがすべて異なるリズムで動く。

**アニメーション干渉の解決策（技術的工夫）：**
複数アニメーションが同じ `transform` を触ると後から適用したものが上書きしてしまう問題を、
アニメーションをDOM要素の階層に分散させることで解決：

```
.bottle-wrapper  → bottleJourney（移動）+ floatBob（上下）
  └── .bottle   → floatWiggle（左右）
       └── img  → floatRotate（回転）
```

**CSS Custom Propertiesによるブリッジ：**
JavaScriptでパラメータを計算 → CSSカスタム変数に設定 → CSSアニメーションが変数を参照。
アニメーション計算をCSSに任せることでメインスレッドをブロックしない。

### ユーザーが「行動したくなる」導線設計

```
① 海を漂うボトルを見る（受動的）
        ↓
② ボトルをクリック → 詳細モーダルがスライドアップ
        ↓
③「行動する」or「後でやる（タスク保存）」
        ↓
④ マイページのタスク一覧から後日Action投稿
        ↓
⑤ ChainViewで自分の行動が連鎖している様子を確認
```

「後でやる」タスク保存機能は、その場で行動できなくてもコミットを維持し、
後日の行動率を高めることを意図した設計。

### いいね最大10回の設計意図

通常の1いいね = 1回ではなく、同一ユーザーが最大10回いいねできる仕様。
「どれほど強く気持ちが伝わったか」を段階的に表現するUX。
上限10回はスパム防止と表現の豊かさのバランスで決定した。

実装はFirestoreのトランザクションで `likesMap[userId]` をインクリメントし、
`< 10` の条件チェックと書き込みをアトミックに実行している。

### 初見ユーザーに伝わりづらかった点と審査員フィードバック

審査員フィードバック：**「世界観は良いが導入がやや分かりづらい」**

- ボトルをクリックするとメッセージが見られることが直感的でなかった
- Thanks と Action の違い・連鎖の仕組みが初見で理解しにくかった
- オンボーディング・チュートリアル画面がなかった

学び：**「世界観設計」と「ユーザー導線設計」は別軸で最適化が必要**

### 現在の課題

- チュートリアル・オンボーディングなし
- スマホでの表示崩れが一部残存（PC開発が中心だったため）
- RankingView・SearchViewは未実装（ルーティングのみ定義済み）
- Firestoreセキュリティルールが緩い設定のまま
- Firebase Storageを使った画像投稿は未実装

## 5. 面接回答

### Q1. Thank x Chain とは何ですか？

「技育展2025のハッカソンで開発した、感謝の連鎖を可視化するSNSです。
SNSの誹謗中傷・炎上といったネガティブな情報環境への問題意識から、
感謝だけを扱うプラットフォームを作りました。

2種類の投稿で成り立っています。『Thanks』は日常の感謝を発信するルート投稿、
『Action』はその感謝を受けて実際に行動したことを返信する投稿です。
このThanks→Action→Actionの連鎖をツリー構造で可視化することで、
善意がどう広がっているかが見えるようにしました。」

### Q2. なぜ作ったのですか？

「チームに今のSNSを使っていてネガティブな投稿に疲れるという問題意識がありました。
感謝やポジティブな出来事は日常にたくさんあるのに、発信されにくい構造だと感じていました。

ブロックチェーンの『連鎖・不変性』という概念からアイデアを得て、
感謝が次の行動を生む連鎖をSNSで表現したいと思いました。
作ってみて気づいたのは、世界観の設計と使いやすさの設計は別軸で最適化が必要だということで、
それが審査員フィードバックに反映されていました。」

### Q3. 技術的に工夫した点は何ですか？

「2点あります。

1つ目はFirestoreでのツリー構造の設計です。
FirestoreはSQLのようなJOINや再帰クエリができないので、
各Actionに `rootPostId`（チェーンの根のID）を持たせ、
`where("rootPostId", "==", rootId)` の1クエリでチェーン全体を取得できる設計にしました。

2つ目はボトルメールのアニメーションです。
4種のCSSアニメーションを同時実行しているのですが、
複数のアニメーションが同じ `transform` を触ると後から適用したものが上書きしてしまいます。
それをDOM要素の階層にアニメーションを分散させることで解決しました。
また、アニメーションのパラメータをCSS Custom Propertiesで受け渡すことで、
計算はJavaScriptで行いつつアニメーション自体はCSSのCompositorスレッドに任せる、
パフォーマンスの高い構成にしました。」

### Q4. FirestoreでツリーをどうやってFlastoreで表現しましたか？

「各Actionドキュメントに3つのフィールドを持たせました。

`depth` は階層の深さで、Thanks（ルート）が0、最初のActionが1です。
`parentPostId` は直接の親投稿のIDで、ChainViewでのSVGコネクタ描画に使います。
`rootPostId` がポイントで、どんなに深い階層のActionでも
チェーンの根（Thanks投稿）のIDを全員が持ちます。

これによってチェーン全体を取得するときは
`where("rootPostId", "==", rootId)` の1クエリで完結します。
Firestoreに再帰クエリがないことへの設計上の回答です。

フロントでは、取得したフラットな配列をdepthでソートし、
同じdepth内で均等にX座標を割り当ててツリーをレイアウト計算し、
親子の接続はSVGのlineで描画しています。」

### Q5. なぜFirebaseを使いましたか？

「ハッカソンの時間制約の中でバックエンドサーバーをゼロから作る余裕がなかったためです。
FirebaseのBaaS構成で認証・DB・ストレージをすべてサービスとして利用することで、
フロントエンドの品質に集中できました。

加えてCloud FirestoreはリアルタイムのonSnapshot購読がネイティブサポートされており、
複数ユーザーの投稿をリアルタイムで反映する機能を低コストで実装できる点も理由のひとつです。

一方でバックエンドがないため複雑なビジネスロジックをサーバーサイドで実行できない点と、
Firestoreのセキュリティルールをしっかり設計しないとアクセス制御が甘くなる点は
課題として認識しています。」

### Q6. なぜUIをボトルメール型に変えましたか？

「最初はタイムライン型で設計していたのですが、開発途中で違和感を覚えました。
タイムライン型だとフォロワー数の多い人の投稿が上位に集まり、
既存SNSと同じ承認欲求ゲームを再現するだけになってしまいます。

それでは『感謝が誰かに届く』という私たちのコンセプトとズレていると感じ、
ランダムに表示するボトルメール型に切り替えました。
フォロワー数に関係なく全員の感謝が等しく届く可能性があり、
世界観とUXの一貫性が保てました。」

### Q7. 最もユーザーを意識した点は何ですか？

「『後でActionする』タスク保存機能です。

感謝投稿を見て行動したいと思っても、その場ではできないことが多いと考えました。
タスクとして保存しておけばマイページから後日Action投稿できる導線にすることで、
ユーザーのコミットメントを維持し、行動率を高める設計を意図しました。

実装面では、タスク保存時に元の投稿内容のスナップショットをtasksドキュメントにコピーしています。
元の投稿が削除されてもタスク一覧が正しく表示されるようにするためで、
FirestoreにJOINや参照整合性がないことへのデータ設計上の対応でもあります。

ただ最終的に審査員から『世界観は良いが導入が分かりづらい』というフィードバックをいただきました。
世界観の設計とユーザー導線の設計は別軸で最適化が必要だと学んだ経験です。」

### Q8. 今ならどう改善しますか？

「3点あります。

1点目はオンボーディングの設計です。
Thanks/Actionの違いや感謝の連鎖の概念を、インタラクティブなチュートリアルで伝えることで
審査員のフィードバックにあった導入の分かりにくさが解消できると思います。

2点目はモバイルファーストへの転換です。
PC中心で開発していたため、スマホでの表示崩れが後から発覚しました。
最初からスマホを基準に実装し、PCへ拡張する順序にすべきでした。

3点目は匿名性の設計の見直しです。
現状は `isAnonymous: true` のフラグでUIレベルの匿名化をしているだけで、
FirestoreにはauthorIdが保存されています。
本番サービスとしては Cloud Functions を経由してauthorIdを除いたデータを書き込む設計が必要です。
ハッカソンスコープでUIレベルにとどめたことは説明できますが、
本番提供には不十分だと認識しています。」

### Q9. Hirolia との違いは何ですか？

|---|---|---|
| 開発コンテキスト | ハッカソン（短期・集中） | （Hiroliaに合わせて補完） |

「Thank x ChainはFirestoreのドキュメント設計と制約に合わせたクエリ設計を深く経験した作品です。
HiroliaはXXXで、Thank x Chainとは異なるXXXの経験ができました。」という形で話してください。

### Q10. この経験が SmartHR でどう活きると思いますか？

「2点あります。

1点目はデータ設計の経験です。
FirestoreでJOINなしにツリー全体を1クエリ取得するための設計判断は、
DBの制約を理解した上でデータモデリングを考えた経験です。
SmartHRのプロダクトでもデータ構造の設計判断が必要な場面で活かせると思います。

2点目は審査員フィードバックからの学びです。
『世界観は良いが導入が分かりづらい』という評価は、
機能を作ることとユーザーに届けることは別の問題だと体感させてくれました。
SmartHRは業務システムなのでユーザーが迷わず使える導線設計が重要だと思っており、
ハッカソンの失敗から得た視点をプロダクト開発に活かしたいです。」

## 6. 深掘り想定問答

### 「チェーンの件数が多すぎる場合はどうしますか？」

「現状の実装では1チェーンのAction投稿をすべて1クエリで取得しています。
件数が多い場合はFirestoreのpaginationを使い、
初期表示はdepth=0,1の投稿に絞り、ユーザーが展開した時だけ深い階層を遅延ロードする方式が考えられます。
ただしハッカソンスコープでは未実装です。」

### 「トランザクションがリトライし続けたら？」

「FirestoreクライアントSDKは競合時に自動リトライしますが上限があり、超えるとエラーになります。
現状のコードはtry-catchでエラーを呼び出し元に伝えています。
本番環境では指数バックオフ付きリトライや、適切なUIフィードバックが必要です。」

### 「なぜPiniaを使わなかったのですか？」

「管理が必要なグローバルstateが『ログインユーザー情報』と『モーダルの開閉状態』の2つだけでした。
Piniaはストア定義・アクション・ゲッターの設定が多く、今回の規模では過剰設計になると判断し、
Vue 3の `ref()` をエクスポートするだけのシンプルな実装にしました。
複数人が非同期でstateを更新するような複雑な要件が出てきたらPiniaへの移行を検討します。」

### 「匿名投稿なのにauthorIdが保存されているのは問題では？」

「ご指摘の通りです。`isAnonymous: true` はUIレベルの匿名化で、著者名を表示しないだけです。
管理者はFirestoreコンソールからauthorIdを確認できます。
本来はCloud Functionsを経由してサーバー側でauthorIdを除いたデータを書き込む設計が必要ですが、
ハッカソンの時間制約の中でUIレベルにとどめました。
本番サービスとしては不十分だと認識しています。」

### 「自己PRにVercelと書いてあるが実際は？」

「実際のデプロイはAWS Amplifyです。`amplify.yml` でGitにpushするたびに
pnpm install → vite build → 静的ファイル配信のCI/CDが自動で走るよう設定しています。
自己PRの記述は誤りで、正確にはAWS Amplifyです。」
