## 1. 技術選定の理由

---

### Q. なぜVue.jsを選んだんですか？ReactやAngularではなく？

**A.**
チームメンバーの多くがVueを学習経験していたためです。
ハッカソンは時間が非常に限られているので、全員が慣れている技術を選ぶのが最優先でした。

技術的な観点でいうと、Vue 3のComposition API（`ref`, `computed`, `watch`など）は、
コンポーネントごとにロジックをまとめやすく、複数人で並行開発する際に役割分担がしやすいです。
また、単一ファイルコンポーネント（`.vue`ファイル）はHTML・CSS・JavaScriptが1ファイルにまとまるため、
UIコンポーネントの単位でタスクを切り分けやすかったです。

---

### Q. なぜFirebaseを使ったんですか？

**A.**
ハッカソンの時間制約の中で、バックエンドサーバーをゼロから構築する時間がなかったためです。
FirebaseのBaaS（Backend as a Service）構成を使えば、
認証・データベース・ストレージをすべてサービスとして利用でき、
フロントエンドの開発に集中できました。

Cloud Firestoreはリアルタイム購読（`onSnapshot`）がネイティブサポートされており、
複数ユーザーの投稿がリアルタイムで反映されるような機能を簡単に実装できるのも選定理由のひとつです。

---

### Q. AWS Amplifyでホスティングしている理由は？

**A.**
GitにpushするだけでCI/CDが走り、自動でビルド・デプロイが完結するためです。
`amplify.yml`に設定を書くだけで、pnpm install → vite build → 静的ファイル配信までを自動化できています。
ハッカソン中の「コードを書いたらすぐ反映したい」という要求に応えられる構成です。

---

### Q. なぜPinia（またはVuex）を使わなかったんですか？

**A.**
このプロジェクトで管理が必要なグローバルstateは、
「ログインユーザー情報」と「投稿モーダルの開閉状態」の2つだけでした。
Piniaはストアの定義・アクション・ゲッターなど設定が多いため、
今回の規模ではオーバーエンジニアリングになると判断しました。

Vue 3の `ref()` をエクスポートするだけで同じことが実現でき、
シンプルなコードで済みます。

```javascript
// store/user.js
export const user = ref(null)

// store/modal.js
export const isPostFormModalOpen = ref(false)
```

---

### Q. pnpmを使っている理由は？npmやyarnではなく？

**A.**
pnpmはnpmと比べてインストールが高速で、ディスクスペースの使用量が少ないです。
仕組みとして、パッケージをグローバルキャッシュに1回だけ保存し、
プロジェクトからはシンボリックリンクで参照するため、
同じパッケージを複数プロジェクトで使う場合でも無駄な重複がありません。
CI/CDのビルド時間短縮にも有効です。

---

### Q. PWAに対応した理由は？

**A.**
スマートフォンのホーム画面に追加できることで、
ネイティブアプリに近い体験を提供できるためです。
`vite-plugin-pwa`を使えばService Workerの設定をほぼ自動で行えるため、
追加コストが低い割にUX向上効果が高いと判断しました。

## 2. アーキテクチャ設計

---

### Q. バックエンドのAPIはどこにあるんですか？

**A.**
このプロジェクトには独立したバックエンドサーバーは存在しません。
FirebaseのSDKを使って、フロントエンドから直接Firestoreにアクセスしています。

これをBaaS（Backend as a Service）構成と呼びます。
アクセス制御はFirestoreのセキュリティルールで行います。

ただしデメリットとして、複雑なビジネスロジックをサーバーサイドで実行できないため、
その部分はCloud Functionsを使うか、後から通常のAPIサーバーを追加する必要があります。

---

### Q. SPAってどういう意味ですか？

**A.**
Single Page Application の略です。
従来のWebサイトはページ遷移のたびにサーバーからHTMLを取得しますが、
SPAは最初に1回だけHTMLを読み込み、以降のページ遷移はJavaScriptで描画を切り替えます。

メリット：ページ遷移が高速、ネイティブアプリのような体験
デメリット：初回ロードが遅くなる可能性、SEOの工夫が必要

このプロジェクトではVue Routerが `createWebHistory` モードで動作しており、
URLが変わっても実際にはページリロードは発生しません。

---

### Q. サービス層（firebaseService/）を作った理由は？

**A.**
UIコンポーネントとFirebaseのアクセスロジックを分離するためです。
もしFirebaseをやめて別のAPIに変更したとしても、
`firebaseService/` 配下だけ書き換えれば、コンポーネント側は変更不要になります。
これを「関心の分離（Separation of Concerns）」と呼びます。

また、複数のコンポーネントから同じ操作（例：いいね）を呼び出す場合に、
ロジックを1箇所にまとめることで重複を避けられます。

---

## 3. 自分の担当部分（ファーストビュー）

---

### Q. ボトルメールUIはどうやって実装したんですか？

**A.**
主にCSSアニメーションとJavaScriptの組み合わせで実装しました。

1. **4種類のCSSアニメーションを同時実行**
   - `bottleJourney`：ボトルが画面上を移動（35〜55秒かけてA→B）
   - `floatBob`：上下に揺れる（海面の波）
   - `floatWiggle`：左右に揺れる
   - `floatRotate`：傾いて回転

2. **各アニメーションのパラメータをランダム化**
   - 移動速度・揺れ幅・開始タイミングをランダムに設定
   - 4つのボトルがすべて違うリズムで動くように

3. **CSS Custom Properties（カスタムプロパティ）でブリッジ**
   - JavaScriptでパラメータを計算 → CSSカスタム変数に設定
   - CSSアニメーションがその変数を参照して動く
   - アニメーション計算をCSSに任せることでパフォーマンスが向上

---

### Q. 物理シミュレーションってどういう意味ですか？

**A.**
ボトル同士が重なって見苦しくならないように、ボトルが互いに「反発」する動きを実装しました。

`requestAnimationFrame` を使って毎フレーム（約60fps）以下の処理を実行します：

1. 全ボトル同士の距離を計算（ピタゴラスの定理 `√(dx² + dy²)`）
2. 距離が閾値（400px）未満なら、離れる方向に力を加える
3. その反発量をCSS変数（`--repel-x`, `--repel-y`）に設定
4. CSSの `transform: translate()` で実際に位置をずらす

これにより、ボトルが重なった状態を自然に回避します。

---

### Q. なぜsetIntervalではなくrequestAnimationFrameを使ったんですか？

**A.**
`requestAnimationFrame` はブラウザの描画タイミングに同期して実行されるため、
`setInterval` と比べてアニメーションが滑らかで、パフォーマンスも優れています。

`setInterval` の問題：
- 実際の描画タイミングと同期していないのでカクつく
- タブが非アクティブでも実行されてCPUを無駄に使う

`requestAnimationFrame` の利点：
- ブラウザの垂直同期（通常60fps）に合わせて実行
- タブが非表示のとき自動的に一時停止してリソース節約

---

### Q. モーダルのドラッグ操作はどうやって実装しましたか？

**A.**
スマホ（タッチ操作）とPC（マウス操作）の両方に対応する実装をしました。

**スマホ：** `touchstart / touchmove / touchend` イベント
**PC：** `mousedown / mousemove / mouseup` イベント

実装の工夫として、`mousedown` 時にはモーダル要素ではなく `window` にリスナーを付けています。
これはモーダルの外でマウスを離しても `mouseup` を正しく検知するためです。

```javascript
const handleMouseDown = (e) => {
  isDragging.value = true
  window.addEventListener('mousemove', handleMouseMove)  // window に追加
  window.addEventListener('mouseup', handleMouseUp)
}
const handleMouseUp = () => {
  window.removeEventListener('mousemove', handleMouseMove) // 後始末
  window.removeEventListener('mouseup', handleMouseUp)
}
```

モーダルを100px以上下にドラッグすると閉じる仕様にしており、
ネイティブアプリのBottomSheetと同じUXを実現しています。

---

### Q. ボトルにホバーしたとき動きが止まるのはなぜですか？

**A.**
CSSの `animation-play-state: paused` プロパティを使っています。

```css
.bottle-wrapper:hover {
  animation-play-state: paused; /* ホバーでアニメーション一時停止 */
  z-index: 10;
}
```

ユーザーがボトルにカーソルを合わせたとき、
ボトルが動き続けるとクリックしにくいため、一時停止させています。
同時に `z-index: 10` でホバー中のボトルを最前面に表示します。

## 4. 難しかったこと・解決したこと

---

### Q. 開発中に一番苦労したことは何ですか？

**A.**
モーダルのドラッグ操作の実装が最も難しかったです。

**問題：**
最初、`mousedown`リスナーをモーダル要素自体につけていました。
しかし、マウスをすばやく動かすとカーソルがモーダル外に出てしまい、
`mousemove`イベントが届かなくなってドラッグが途中で止まる問題が発生しました。

**解決策：**
`mousedown` 時にだけ `window` 全体にリスナーを付けることで解決しました。
`window` はページ全体を覆っているため、カーソルがどこに移動しても追跡できます。
`mouseup` 時にはリスナーを削除してメモリリークを防ぎます。

---

### Q. ボトルのアニメーションで難しかったことは？

**A.**
複数のCSSアニメーションを同時に動かしたとき、
アニメーション同士が干渉して意図しない動きになる問題がありました。

`transform` プロパティを複数のアニメーションで同時に変更しようとすると、
後から適用されたものが前のものを上書きしてしまいます。

**解決策：**
アニメーションを要素の階層に分割しました。
- 外側の `.bottle-wrapper` → 移動（journey）と上下揺れ（bob）
- 中間の `.bottle` → 左右揺れ（wiggle）
- 内側の `.bottle-image` → 傾き回転（rotate）

各アニメーションを別の要素に割り当てることで干渉を回避しました。

---

### Q. Firestoreでデータ取得がうまくいかなかったことはありましたか？

**A.**
チェーン（感謝の連鎖）を取得する `getPostChain` 関数の実装で詰まりました。

**問題：**
感謝投稿（Thanks）から始まるすべての返信（Action）を再帰的に取得しようとしていましたが、
Firestoreは再帰クエリをサポートしていないため、実装が複雑になりました。

**解決策：**
すべてのAction投稿に `rootPostId`（最初のThanks投稿のID）フィールドを持たせる設計にしました。
チェーン全体を取得する場合は、`rootPostId == 対象ID` でフィルタリングするだけで
ツリー全体を1クエリで取得できます。

```javascript
// 例：rootIdに紐づくAction投稿をすべて取得
const q = query(postsCollection, where("rootPostId", "==", rootId))
```

データ設計を工夫することでFirestoreの制限を回避しました。

---

### Q. チームで開発するときに困ったことはありましたか？

**A.**
ブランチ管理とマージコンフリクトが発生しました。
複数人が同じファイルを同時に編集することがあり、
マージ時に競合が起きました。

対応として、コンポーネント単位・ページ単位でタスクを分担し、
できるだけ同じファイルを触らないように調整しました。
また、PRをこまめに出してレビューする習慣をつけることで、
大きな差分が一度に来ないようにしました。

## 5. データベース・API設計

---

### Q. データベースの設計を説明してください

**A.**
Cloud Firestoreを使っており、主に3つのコレクションがあります。

**posts コレクション：** 投稿本体
```
{
  type: "thanks" | "action",  // 感謝投稿 or 行動投稿
  text: string,               // 本文
  authorId: string,           // 投稿者のUID
  isAnonymous: boolean,       // 匿名フラグ
  timestamp: Timestamp,
  likeCount: number,
  depth: number,              // 0=ルート, 1以上=返信
  parentPostId: string,       // 親投稿のID（Actionのみ）
  rootPostId: string,         // チェーンの根（Actionのみ）
  likesMap: { [uid]: number } // ユーザーごとのいいね数
}
```

**tasks コレクション：** タスク保存
```
{
  userId: string,
  postId: string,
  status: "pending" | "completed"
}
```

**users コレクション：** ユーザープロフィール
```
{
  uid: string,
  displayName: string,
  email: string
}
```

詳しくは `03_DB設計とAPI設計.md` を参照。

---

### Q. いいねの実装でトランザクションを使っているのはなぜですか？

**A.**
複数のユーザーが同時にいいねを押したとき、データの整合性を保つためです。

いいねの処理では：
1. 現在のいいね数を読む
2. +1 して書き込む

この「読む」と「書く」の間に別のユーザーが同じ操作をすると、
正しいカウントにならない（競合状態）が発生します。

Firestoreのトランザクション（`runTransaction`）を使うと、
読み取りと書き込みをアトミック（一体不可分）に実行できます。
誰かが同時に操作していたら、自動的にリトライされます。

---

### Q. なぜいいねは1ユーザー最大10回なんですか？

**A.**
「気持ちの強さを段階的に表現できる」UXを実現したかったからです。

通常のSNSは1いいね = 1回だけですが、
このアプリでは「本当に感謝した」「めちゃくちゃ共感した」という気持ちを
最大10回まで押すことで伝えられます。

同時に無制限にするとスパムの温床になるため、上限を10回に設定しました。

## 6. パフォーマンス・最適化

---

### Q. パフォーマンスで気を使った点はありますか？

**A.**
いくつか意識した点があります：

**① アニメーションはCSSで処理**
JavaScriptで毎フレーム位置を計算するよりも、
CSSアニメーションはブラウザのCompositorスレッドで実行されるため、
メインスレッドをブロックせずに滑らかに動きます。

**② requestAnimationFrameの後始末**
コンポーネントが破棄される（別のページに移動する）とき、
`cancelAnimationFrame` でアニメーションループを停止しています。
停止しないとメモリリークやバックグラウンドでのCPU消費が発生します。

**③ Firestoreのクエリ最適化**
全投稿を取得してフロントでフィルタリングするのではなく、
`where("type", "==", "thanks")` のようにクエリ段階でフィルタリングしています。

**④ ランダム表示（4件のみ）**
全投稿を取得しても画面には4件しか表示しません。
`selectRandomBottles()` でランダム抽出し、残りはメモリ内に保持。
「別のボトルを探す」ボタンを押したときはFirestoreに再アクセスせず、
取得済みデータからランダム選択します。

## 7. セキュリティ

---

### Q. セキュリティ面で考慮したことはありますか？

**A.**
Firebaseの環境変数管理とFirestoreのセキュリティルールについて考慮しました。

**環境変数：**
FirebaseのAPIキーなどは `.env.local` ファイルに記述し、Gitにはコミットしていません。
（`.gitignore` で除外）

**注意点：**
ViteのフロントエンドプロジェクトはビルドするとAPIキーがJavaScriptバンドルに含まれます。
FirebaseのAPIキーは公開されること自体はある程度許容されており、
実際のアクセス制御はFirestoreのセキュリティルールで行います。

**Firestoreセキュリティルール：**
認証されたユーザーのみ読み書きできる設定が基本です。
例えば「自分の投稿しか削除できない」といったルールを記述できます。

---

### Q. 匿名投稿機能でプライバシーはどう保護していますか？

**A.**
`isAnonymous: true` が設定された投稿では、
フロントエンド側で著者名の表示を変更し、「匿名ユーザー」として表示します。
ただし `authorId`（UID）自体はFirestoreに保存されているため、
管理者レベルでは投稿者を特定できます。

完全な匿名性が必要であれば、Cloud Functionsを経由して投稿する設計が必要です。
ハッカソンスコープではUIレベルの匿名化にとどめました。

## 8. チーム開発・Git運用

---

### Q. Gitでどうやって開発を進めましたか？

**A.**
GitHub Flowに近い形で運用しました。

- `main`：リリース用ブランチ
- `deploy-AWS`：AWS Amplify用デプロイブランチ
- `develop/*`：機能開発用ブランチ
- `hotfix/*`：緊急修正用ブランチ

新機能は `develop/機能名` ブランチを切って開発し、
Pull Requestを経由して `main` にマージしました。

### Q. コードレビューはしましたか？

**A.**
Pull Requestを通じてレビューを行いました。
ハッカソンという時間制約の中でもPRを分けることで、
他のメンバーが変更を把握しやすい運用を心がけました。

## 9. 振り返り・改善点

---

### Q. 今振り返って、こうすればよかったと思うことはありますか？

**A.**
3点あります：

**① ユーザー導線の設計**
審査員から「世界観は良いが導入が分かりづらい」とフィードバックをいただきました。
アプリの操作方法が直感的でなく、初めてのユーザーが迷う場面がありました。
チュートリアル画面やオンボーディングフローを設計すべきでした。

**② モバイルファーストの徹底**
PCでの開発が中心だったため、スマホでの表示崩れが後から発覚しました。
最初からモバイルファーストで実装し、レスポンシブ対応を先行させるべきでした。

**③ Firestoreセキュリティルールの整備**
ハッカソン期間中はセキュリティルールが緩い設定のままで、
本来なら本番リリース前に必ず整備すべき部分です。

---

### Q. このプロジェクトで一番成長できた部分はどこですか？

**A.**
CSSアニメーションとJavaScriptを組み合わせたUI実装の経験です。

アニメーションのパラメータをCSS Custom Propertiesで動的に変更する手法は、
このプロジェクトを通じて習得しました。
また `requestAnimationFrame` を使ったゲームループの概念（物理シミュレーション）も
初めて実装し、フロントエンドエンジニアとしての幅が広がりました。

---

### Q. もし時間があれば追加したかった機能は？

**A.**
**① 検索機能**
タグやキーワードで投稿を検索できる機能（SearchViewのルートは定義済み）

**② ランキング機能**
いいね数の多い投稿や、アクション数の多いユーザーのランキング

**③ 通知機能**
自分の投稿にActionがついたときにプッシュ通知を受け取る機能

**④ 画像投稿**
Firebase Storageは設定済みのため、実装自体は可能な状態
